# 5주차 개인 회고

## 이번 주에 한 일

- Spring Boot 애플리케이션을 멀티 스테이지 Docker 이미지로 만들었다.
- Docker Compose로 애플리케이션, MySQL, Redis를 함께 실행했다.
- Flyway를 적용해 빈 운영 DB에서도 스키마가 자동으로 생성되게 했다.
- 캐시 비활성/활성 서버를 같은 조건에서 k6로 부하 테스트하도록 구성했다.
- EC2와 RDS 배포 과정, 보안 그룹, 헬스 체크와 트러블슈팅 절차를 정리했다.

## 배운 점

컨테이너가 빌드되는 것과 실제 서비스가 준비되는 것은 다르다. DB와 Redis가 먼저
준비되어야 하므로 health check와 `depends_on` 조건이 필요했다. 또한 운영 설정에서
Hibernate를 `validate`로 두려면 테이블 생성 책임을 Flyway 같은 마이그레이션 도구가
맡아야 한다는 점을 배웠다.

캐시 성능은 단순히 한 번 빠른 응답을 확인하는 방식보다 같은 데이터, 같은 요청률,
같은 측정 시간으로 비교해야 의미가 있었다. 평균만 보면 순간 지연을 놓칠 수 있어 p95,
최대 응답 시간, 실패율과 처리량을 함께 확인했다.

## 어려웠던 점과 해결

운영 프로파일은 처음부터 스키마가 존재한다고 가정해 새 RDS에서 기동에 실패할 수 있었다.
Flyway 초기 마이그레이션을 추가하고 애플리케이션 시작 단계에서 스키마를 만든 뒤 JPA가
검증하도록 책임을 분리했다.

캐시 전/후를 공정하게 비교하기 위해 동일한 MySQL을 사용하는 두 애플리케이션 인스턴스를
구성했다. 하나는 Redis 캐시를 활성화하고 다른 하나는 캐시 기능을 비활성화했으며, k6의
요청률과 시간을 고정했다.

## 다음에 개선할 점

- AWS에서는 ALB와 HTTPS를 적용하고 8080 포트를 인터넷에 직접 공개하지 않는다.
- 비밀번호는 Secrets Manager에서 주입하고 이미지 저장소는 ECR을 사용한다.
- 조회뿐 아니라 쓰기 혼합 시나리오와 캐시 적중률도 측정한다.
- 실제 AWS 환경에서 테스트를 3회 이상 반복해 중앙값과 인스턴스 사양을 함께 기록한다.
