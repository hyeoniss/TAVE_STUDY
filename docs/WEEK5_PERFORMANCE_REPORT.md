# 캐시 적용 전/후 k6 부하 테스트 보고서

## 테스트 목적

동일한 Todo 목록 조회 요청을 캐시 비활성 서버와 Redis 캐시 활성 서버에 각각 보내
응답 시간과 처리량의 차이를 비교한다.

## 테스트 환경

- API: `GET /api/todos?page=0&size=100`
- 데이터: 최소 200개 Todo
- 부하 모델: constant arrival rate
- 목표 부하: 100 requests/second
- 측정 시간: 30초
- 성공 조건: 실패율 1% 미만, p95 500ms 미만
- 캐시 비활성 서버: `http://localhost:8081`
- Redis 캐시 활성 서버: `http://localhost:8080` (측정 전 1회 호출로 warm-up)

## 실행 방법

```bash
chmod +x scripts/run-cache-benchmark.sh
./scripts/run-cache-benchmark.sh
```

원하는 부하와 시간으로 바꾸려면 다음처럼 실행한다.

```bash
TARGET_RPS=200 DURATION=1m ./scripts/run-cache-benchmark.sh
```

원본 결과는 `k6-results/no-cache.json`, `k6-results/cache.json`에 저장된다.

## 결과

| 구분 | 총 요청 수 | 처리량(req/s) | 평균(ms) | p95(ms) | 최대(ms) | 실패율 |
|---|---:|---:|---:|---:|---:|---:|
| 캐시 미적용 | 3,001 | 99.87 | 2.61 | 4.85 | 29.20 | 0.00% |
| Redis 캐시 적용 | 3,001 | 99.96 | 2.98 | 4.67 | 38.14 | 0.00% |

측정일은 2026-10-12이며 로컬 Docker 환경에서 각 조건을 1회 측정했다. setup 단계의
헬스 체크와 테스트 데이터 생성 요청은 위 집계에서 제외했다.

개선율은 `(미적용 값 - 적용 값) / 미적용 값 × 100`으로 계산한다. 응답 시간은 값이
낮을수록, 처리량은 높을수록 좋다.

## 해석 시 주의점

- 이 테스트는 목록 조회 성능만 비교하며 등록·수정·삭제 성능을 대표하지 않는다.
- 두 서버는 같은 MySQL 데이터를 사용하지만 서로 다른 포트에서 실행된다.
- 캐시 서버는 warm cache, 비활성 서버는 매 요청마다 DB 조회 조건이다.
- 로컬 Docker 결과는 네트워크와 인스턴스 사양이 다른 AWS 결과와 분리해서 기록한다.
- 정확도를 높이려면 같은 조건으로 3회 이상 실행하고 중앙값을 사용한다.

## 결론 작성 예시

Redis 적용 후 p95 응답 시간은 `[A]ms`에서 `[B]ms`로 `[C]%` 감소했고, 처리량은
`[D] req/s`에서 `[E] req/s`로 `[F]%` 증가했다. 반복 조회에서 DB 접근을 생략한 것이
주요 원인이다. 데이터 변경 시 `@CacheEvict(allEntries = true)`로 목록 캐시를 제거해
정합성을 유지하지만, 쓰기가 잦으면 캐시 적중률과 제거 비용을 추가로 확인해야 한다.

## 이번 측정 결론

100 req/s 조건에서 두 구성 모두 목표 요청률을 처리했고 실패는 없었다. Redis 적용 후
p95는 4.85ms에서 4.67ms로 약 3.71% 감소했지만, 평균은 2.61ms에서 2.98ms로 약
14.18% 증가했다. 처리량 차이는 약 0.09%로 사실상 동일했다. 현재 데이터가 200개로
작고 MySQL이 같은 로컬 머신에 있어 DB 조회 자체가 충분히 빠르며, Redis 조회와 JSON
직렬화·역직렬화 비용이 상쇄된 것으로 해석할 수 있다.

따라서 이번 결과만으로 캐시가 전반적으로 성능을 개선했다고 결론 내리기는 어렵다. 실제
AWS의 EC2-RDS 네트워크 환경, 더 큰 데이터셋, 300~1,000 req/s 구간에서 3회 이상
반복해 중앙값을 비교하는 후속 측정이 필요하다. 다만 p95가 소폭 개선된 점은 반복 조회의
꼬리 지연을 줄일 가능성을 보여준다.
